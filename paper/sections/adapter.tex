\section{The simulator adapter and the contention model}
\label{sec:adapter}

% claim: C34
\paragraph{Compiling a placement, and naming what was lost.}
The adapter turns a placed candidate into a simulator configuration, passing
what can be expressed per placement: a tensor-parallel group is given its own
bottleneck---the minimum over every rank pair of that pair's best path, each
link given its measured all-reduce bus bandwidth at the group's own number of
ranks where the cluster description carries one and its edge capacity
otherwise, capped by what its shared resource's reservations leave---so two
placements of one template on different wires compile to different inputs.
That is the corrected adapter; the registered hardware rows were predicted by
an earlier one that read the group's first rank pair at its edge capacity
(Section~\ref{sec:eval-hw}). What cannot be expressed is which resources two
flows share: two placements with equal bottlenecks that cross different shared
resources compile to the same input. Every compiled plan carries a report of
the shared resources dropped. The report covers that loss and no other: the
rank pairs the earlier adapter ignored were never in it. Folding contention
into the bandwidth instead would make the simulator's output unattributable.

% claim: C10
% claim: C13
\paragraph{Prediction accuracy and search accuracy.}
Whether the simulator predicts hardware well is a property of the simulator;
whether the search finds what an exhaustive oracle finds is a property of the
search, asked by running both against the same evaluator. That needs the
predictor bound to each embedding: one asked about a template returns the
same metrics for every placement of it, which makes \texttt{mismerged\_pairs}
structurally zero. The binding is a named function, and the oracle's result
cache leads with the embedding's identity for the same reason; it is a
different cache from the bucket key of Section~\ref{sec:candidates}, where
sharing a prediction within a class is the saving being claimed.

\paragraph{Contention.}
Flows that share a resource are priced by processor
sharing~\cite{kleinrock1967,massoulie1999}: the active flows
on a resource divide what capacity it has left, a flow's rate is the minimum
over its path, and the schedule is recomputed whenever a flow starts or
finishes. It is not packet-level, and candidates do not contend with each
other: they are alternatives, and only one is deployed. Traffic that is not
the candidate's own enters as a standing reservation of its duty cycle, an
assumption the hardware contradicts (Section~\ref{sec:eval-pd}).
